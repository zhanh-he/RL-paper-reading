TRL / Miles / VeRL

本项目采用两条明确的训练路线：离散音频 token 的 AR 策略用 TRL；连续声学策略的 Flow-GRPO 用 Miles-Diffusion。不再并行维护 VeRL 对照路线。框架已选定，不代表所有模型已完成迁移。

AR：YuE2、Muse 为什么用 TRL

决定性源码依据：所审阅的 Miles-LLM 版本支持 HF-native FSDP2，但其 LoRA 校验要求 train_backend == megatron；FSDP LoRA 尚未实现。采用它不是简单替换 Trainer，还要验收 Megatron/Bridge、adapter 映射和 SGLang serving 的三方一致性。校验源码 · 官方 LoRA 说明

关注点TRLMiles-LLM本项目判断
稳定性策略一致性兼容的 HF actor + PEFT；允许项目内接入原生采样及 log-prob。无需为采用 LoRA 强制转换到 Megatron。有 TITO、恢复与训练/推理一致性工具；当前 LoRA 训练仍需要 Megatron 路线与 serving 映射。选 TRL，减少音频模型移植面。这是工程风险判断，不是故障率对比实测。
速度全链路可用原生生成，也可用 vLLM。Muse 不必为了统一框架而退回 HF-only 生成。SGLang、多机并行、异步调度具有大规模优势；不等于在小模型 / G2 / 单卡上必然更快。没有 YuE2/Muse 的匹配吞吐对比，不填虚构倍数。先复用现有原生音频路径。
显存单卡优先PEFT 可关闭 adapter 计算基座 reference，前提是它确为所选参考策略；可避免额外常驻完整 reference。支持 colocate / offload，但当前 AR LoRA 需要 Megatron；不能把 diffusion 的 FSDP2 LoRA 支持算到这里。TRL + microbatch / checkpointing；codec 与 scorer 分阶段驻留。不是所有 TRL 配置都比 Miles 省显存。

不能交给默认值的四件事

  1. KL 必须显式启用。所审 TRL 0.24 默认 beta=0。本项目拟使用 beta=0.01，并核验 reference identity 与更新后漂移；采样 k3 KL 不是精确全词表 KL，也不是硬约束。
  2. 采样与 loss 必须是同一个策略。YuE2 的 codec+EOS 支持集、最短长度 EOS mask、temperature / CFG、padding 和截断规则都要对齐，不能直接用全词表 teacher forcing 顶替。保留原生 token ID，不做音频 token 的文本往返转换。
  3. 旧策略概率来自真实 rollout。Muse 需检查 vLLM 与 trainer 的 log-prob 差异及 LoRA 版本；HeartMuLa 的八个 codebook 都进入目标，不只训练 codebook0。
  4. 换 TRL 不会自动让 clipping 生效。如果每组仅从旧策略更新一次，第一次梯度的 ratio 为 1，裁剪不会额外限制这次更新。loss normalization、更新次数和 scheduler 必须明确记录，不能只写“GRPO”。

已验收的 HeartMuLa runner 固定在 TRL 0.24.0；Muse 保留其现有兼容环境，不为了版本号整齐而强制升级或降级。新的 TRL rollout API 不能冒充旧版已验收接口。TRL 0.24 官方文档

Flow：为什么选 Miles-Diffusion，而不是 VeRL-Omni

Miles-Diffusion 的 native model backend、batch、SDE 和 loss 接口，以及直接的同步 generate / update / sync 流程，更适合本项目保留原生音频语义、集中排错。这不是已测出 Miles 全面更快或更稳。

关注点Miles-DiffusionVeRL-Omni本项目取舍
稳定性音频接入原生 backend 与细粒度 hooks；默认工厂仍启动 SGLang，引擎创建和音频 worker 需要项目扩展。有 non-diffusers 路线、FSDP2 和恢复测试；当前文档要求上游 vLLM-Omni pipeline 支持。只实现 Miles 的同步音频训练链，不同时维护第二套引擎 port。
速度不套用图像结论支持 LoRA-only 同步和分阶段 offload；尚无本项目全链路吞吐。官方约 25% 提速针对 Qwen-Image 对原版 Flow-GRPO，不是相对 Miles 或音乐模型。不宣称性能胜负；先减少新增组件和非必要调度。官方性能口径
显存能力不等于实测FSDP2、LoRA、checkpointing、offload、关闭 LoRA 的基座 reference。同样有 FSDP2、LoRA、checkpointing、offload、reference-in-actor。没有已验证的显存胜者。单 GPU 的 FSDP 不会凭空产生跨卡分片节省。

已经纠正的两个比较口径

依赖：两套完整环境都涉及 Transformers 5.x 等新依赖，都会与部分原生 4.x 音频环境冲突。必须隔离环境，不能将“无依赖冲突”列为 Miles 的优势。

KL：同一组 Flow-SDE 转移的源码核验中，两家默认 KL 都按 diffusion scale 而非包含步长的完整转移方差归一化。它可以是时间加权正则，但不能叫精确离散转移 KL。下表是 CPU 合成数值夹具，不是歌曲质量或完整框架测试。

所选音频 port 将显式记录冻结 reference 的 conditional Gaussian KL / active latent dimension；rate-scaled 诊断另行命名，排除 padding 和零方差确定性步。两种 KL 的 beta 数值不可不加说明地互换。两个已审 loss 都使用维度平均 log-density ratio，而非联合高斯密度 ratio。

仍未验收：完整 Miles 的音频 rollout → 评分 → 更新 → adapter 同步 → 再生成 → 保存恢复链。自定义 rollout flag 本身不替换默认引擎工厂，train-only 也不能冒充在线训练。通过隔离 loss 不等于通过此链。
